# Bounded recurring content planning

Canvas can create 2–12 consecutive planning cycles within 366 days. The first plan starts immediately; subsequent plans start at midnight (or the first valid local minute) on the first date of their own horizon. Daily, weekly and custom horizons use the same mechanism. The timezone is fixed when the loop is created; daylight-saving transitions use the existing local-calendar resolver. Entirely nonexistent local dates reject the transaction.

The customer explicitly consents to recurring text-planning charges and supplies a total USD budget. The chosen provider/model remains fixed. Both the existing expiring business provider allowance and the loop's aggregate reservation ceiling must permit each model call. No fallback, automatic image/video generation, video-prompt approval or social publication is implied. Already submitted calls can finish and remain charged after stopping. Ambiguous calls hold their reservation and block later loop spending.

Migration 029 adds business-scoped loop records, immutable execution snapshots, loop-linked reservations and `job_dispatch.available_at`. Every occurrence is an ordinary `plan.generate` job with its existing Temporal workflow, idempotency, permissions and recovery. A single transaction saves every occurrence and the dispatch dates; no in-memory timers or customer API credentials are added. The existing dispatcher claims only due rows. One unfinished loop per business is permitted, while future occurrences do not prevent an independent immediate plan. All normal plan-count, daily-request and provider limits remain applicable.

Each occurrence refreshes the latest approved Brand Brain and current goal/channel preferences immediately before its first execution. It persists the exact execution input/hash/brain identity once; retries reuse that immutable snapshot. Original request intent, selected model, start date, horizon and timezone remain unchanged. Scoped worker policies permit reading current brand context for loop jobs without opening other businesses. Workers cannot approve generated posts or change loop spending limits.

Stopping a loop persists its stopped timestamp and requests cancellation for pending/running occurrences. The worker checks cancellation and loop state before spending and checks permission again before promotion. Existing generated plans and approval history remain available. Loops are bounded rather than silently renewing forever; the user can create a new loop with fresh consent after completion or stopping.

Verification includes actual PostgreSQL RLS, separate dispatcher/worker roles, due-time claims, original isolated skills, updated approved facts, immutable snapshots, stop/role denial, per-loop spending and uncertain-call holds. Paid model responses are explicitly MOCK. Canvas browser coverage exercises recurring consent, persisted completion counts and stopping. Deployed scheduling, live model quality/cost acceptance and long-running production behavior remain unverified.
