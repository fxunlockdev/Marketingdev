# ADR 0006 — document evidence and the V5 business experience

The owner's V5 correction replaces the prior client-first UI and blue/white palette. It does not replace the architecture. Account is the existing organization; business is the existing brand. Additive migrations 004–006 provide document provenance/approved knowledge, account entitlements/business grants, and resumable onboarding preferences. Existing migrations 000–003 remain untouched.

The standard allowance defaults to three businesses in `account_entitlements`. A database trigger serializes creates, regardless of request key. All non-archived records count; archival is not implemented, so no record is silently removed from the count. Paid upgrade availability is false until billing exists. First verified app entry initializes a personal account once, creates zero businesses, and shares a lock across simultaneous requests. The old workspace-create application route rejects requests once that user's personal account exists. Existing legacy accounts are not merged/deleted or reclassified automatically.

New `business_memberships` narrow account memberships marked `business_scope=selected`. Restrictive RLS applies to brands, files, jobs, source chunks/findings, approved profiles and audit/outbox rows. API transactions recheck access for a selected business; workers recheck the original requester and business grant before saving results. Selected seats cannot use account-wide team administration. Full role semantics and business-specific invitations remain unfinished; the V5 Team page does not expose the old broad invitation controls.

`brand_sources` and `brand_chunks` retain source hash, exact text and page/slide anchor. Finding edits cannot rewrite original evidence. All findings begin unreviewed; Correct/Wrong/Edit use optimistic revisions and a serialized draft revision. Only account owner/admin approval creates an immutable Brand Brain snapshot; all findings must be reviewed, accepted values for a field must agree, and name/offering/audience are required. Canonical sorted JSON defines the snapshot SHA-256. New evidence keeps the older approved version active until reviewed/approved. Sources, chunks and approved versions have no runtime update/delete grants.

Document extraction is a separate durable Temporal activity from file validation. It uses only previously malware-scanned canonical bytes and checks their digest again. Its worker cannot mutate a validated asset. Retryable local failures have bounded retries; cancel/revoked membership checks run before processing and before transactional insertion. Retries deduplicate one source per asset/parser version. Account/business quotas bound uploads and document submissions; per-brand review state limits sources/findings to 100/500. Source text never becomes agent/tool instructions.

## Parser contract and isolation

Pinned `docling-slim[convert-core,format-pdf,format-pptx]==2.141.0`, `docling-core==2.103.1`, exact transitive hashes in apps/ingestion/uv.lock and requirements.lock. The actual native PDF path uses DocumentConverter/NativePdfFormatOption/NativePdfPipelineOptions; PPTX uses the actual format backend. No model weights or paid calls are needed for this embedded-text path. Coverage is explicitly `embedded_text_only`. It does not establish full OCR, table, logo, typography, reading-order or visual-layout understanding. Textless documents fail with DOCUMENT_NEEDS_OCR_OR_MANUAL_REVIEW.

Input is stdin, at most 20 MiB; output is bounded and independently validated against the input hash, expected parser version, valid pages/bounding boxes and allowed schema. At most 50 pages, 2,000 chunks, 250,000 characters. PPTX ZIP validation rejects traversal, links, encrypted entries, macros, duplicate paths and expansion limits. The parser process receives no credentials, host mounts or networking. The dedicated launcher uses an exact local image SHA, non-root UID, read-only root, tmpfs scratch, no capabilities/new privileges, 1 CPU/1 GiB/64 PIDs, CPU/time limits and bounded stdout. Image build context excludes all files other than Dockerfile/lock/parser.

The launcher currently requires a trusted isolated worker host with Docker. This is locally tested and **not** a promise that nested Docker works inside Railway. Production needs a separate authenticated sandbox-execution service/host, with hardened boundary, scheduling and cleanup. Do not mount a Docker socket into the public API or allow customer-selected container args/images. Parser TTL bounds orphan lifetime after abrupt worker loss; durable retry/dedup handles saved evidence.

Primary contracts inspected: [Docling converter](https://docling-project.github.io/docling/reference/document_converter/), [pipeline options](https://docling-project.github.io/docling/reference/pipeline_options/), [document model](https://docling-project.github.io/docling/reference/docling_document/), plus actual pinned wheel source. Actual PDF/PPTX fixtures test these contracts; they are not customer/generated creatives.

## Experience

Owner's three-step flow: Your business → Confirm your brand → Review goals & finish. Final behavior must pre-fill AI recommendations from website/uploaded evidence and confirmed brand facts, cite supporting sources, label suggestions/uncertainty and ask only for missing information. The current implementation provides manual evidence/goal fallback and explicitly labels defaults as not AI analysis. It must not say “analyzed” or “plan generated” until those jobs exist and succeed.

Warm cream #f5ead8, ink #201e1d, terracotta #c67139 and sage remain the visual basis. Darker terracotta is used for readable text/focus; primary buttons use ink. No copied sample brands, posts or invoices. Eleven destinations appear in the owner-requested order. Unimplemented workflows have truthful unavailable states and no fake success actions. Reference previews are never used as production data.
